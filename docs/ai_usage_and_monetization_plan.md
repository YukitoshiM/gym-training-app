# BodyMode AI利用制限・収益運用計画

更新日: 2026-08-21

公開段階は`monetization_strategy_summary.md`、AIクレジット・広告・購入要件は`ai_credit_monetization_requirements.md`を正本とし、本書では既存のAI利用枠と運用実装を記録する。

機能別の日次・期間利用枠はサーバー保護の上限であり、無料AI枠ではない。通常ユーザーがAIを実行するには、利用枠に余裕があることに加えてAIクレジット残高が必要となる。日付変更で利用枠はリセットされても、AIクレジットは補充されない。

## 1. 目的

Mac miniのAIを一部ユーザーの連打で占有させず、全テスターが安定して使える状態を維持する。利用制限は課金誘導ではなく、公平利用とサーバー保護を第一目的とする。

目標構成はAdMob固定バナー、任意の報酬広告、StoreKit消耗型IAPによるAIクレジットとする。既存の日次利用枠は、クレジット基盤完成までの暫定保護と、完成後の不正利用・混雑保護に使用する。

## 2. 現在地

実装済み:

- 端末ごとの短期アクセストークン、失効、Keychain保存
- 端末・APIごとの30回/分のレート制限
- トークン発行の端末8回/分、全体120回/分の制限
- AI推論の全体同時実行1件と待機タイムアウト
- `429`、通信失敗、モデル失敗時も手動記録を継続できるUI
- iPhone共通ルート上部のAdMob固定バナー、UMP、非パーソナライズ広告
- SQLiteで再起動後も維持される機能別の日次・期間利用枠
- 成功時だけ確定し、失敗時は返却する仮確保方式
- `X-Request-ID`による利用枠の二重計上防止
- `GET /v1/usage`とAIハブの残り回数・リセット時刻表示
- 短時間レート制限、利用枠到達、サーバー混雑、モデル失敗の構造化エラー
- 本文・画像・健康値・直接識別子を含まない件数、平均、p50/p95処理時間のローカル集計

不足:

- AdMob収益とAI負荷を個人データへ結合せず比較する週次運用
- 正式公開後の実績に基づく上限値の調整
- オーナー専用登録キーに紐づく利用枠免除と、キーの失効・再発行

## 3. 全配布版共通の利用枠

TestFlightと正式公開で利用枠を切り替えず、全配布版で次の初期利用枠を常時有効にする。`release_production_preflight.sh`に加え、TestFlight用preflightでも`AI_QUOTA_ENFORCEMENT=1`を必須条件とする。配布経路に依存する例外をなくし、設定ミスで一般ユーザーが無制限になることを防ぐ。

単位はアカウントではなく、短期トークンに含まれる匿名化済みインストールIDとする。再インストールによる回避は可能なため、全体上限と同時実行制限も併用する。

| AI機能 | 初期上限 | 理由 |
|---|---:|---|
| AIトレーナーチャット | 5回/日 | Mac mini単独運用で相談機会を残しつつ負荷を抑える |
| 食事解析（写真・テキスト合計） | 3回/日 | 朝・昼・夕の主要3食を優先する |
| 体型写真解析 | 1回/日 | 複数方向を1セットにまとめて解析する |
| トレーニング計画の生成・修正 | 2回/日 | 初回提案と1回の修正を許容する |
| 日次提案のAI補正 | 1回/日 | ローカル提案を基本とし、AI補正は1回に限定する |
| 週次レポート | 1回/7日 | 週次生成を1回に限定する |
| 月次レポート | 1回/31日 | 月次生成を1回に限定する |

接続確認、コーチ一覧、認証、端末内ルールによる提案、手動記録、履歴閲覧は利用枠を消費しない。AIサーバー側の失敗は原則として枠を消費しない。

### Reddit公開ベータ中の一時上限

2026-08-17〜2026-09-13は、チャット10回/日、食事6回/日、体型写真2回/日、計画4回/日、日次補正2回/日、週次2回/7日、月次1回/31日とする。短時間レート制限、同時実行制御、待機タイムアウトは変更しない。ベータ終了時に利用率、到達率、混雑拒否率、支払意思を確認し、正式公開値へ戻すか再設定する。

### オーナー利用枠

運営者本人は、専用登録キーから発行された`subject`に限って機能別の日次・期間利用枠を免除する。端末の`installation_id`だけを許可リストへ登録せず、機種変更後も専用登録キーで再登録できるようにする。

- 一般ユーザーと通常テスターには既定の利用枠を適用する
- オーナーにも短時間レート制限、同時実行1件、待機タイムアウトを適用してサーバーを保護する
- オーナー登録キーは個別に失効・再発行できるようにする
- オーナー判定、登録キー、内部`subject`をアプリ画面、利用台帳、診断ログへ平文で出さない
- TestFlight全体の上限無効化とは独立して判定し、一般公開版とTestFlightを同時運用できるようにする

## 4. サーバー実装

1. SQLiteへ`ai_usage_ledger`を追加し、匿名化済みインストールID、機能、期間、成功回数、推論時間だけを保存する。
2. 会話本文、画像、健康値、種目名、食事名、APIキー、アクセストークンは利用台帳へ保存しない。
3. `/v1/agents/chat`は`purpose`で`chat`、`plan_generation`、`daily_recommendation`を区別する。
4. 上限は環境変数またはローカル設定ファイルで変更し、アプリ更新を不要にする。
5. `GET /v1/usage`で`enforced`、`limit`、`used`、`remaining`、`reset_at`を返す。オーナー免除時は権限名を露出せず、利用枠が適用されない状態だけを表示する。
6. `429`を`burst_rate_limited`、`daily_quota_exceeded`、`server_busy`へ分類し、`Retry-After`を返す。
7. 日別の機能別件数、成功率、p50/p95処理時間、待機拒否率を内容なしで集計する。

## 5. アプリUX

- 全配布版で同じ残り回数を使い、常時ホームへ出さず、各AI画面、残り3回以下、制限到達時だけ表示する。オーナー免除時だけ利用上限なしと表示する。
- 日次上限では「本日のAI利用上限に達しました。明日リセットされます」とリセット時刻を表示する。
- 混雑時は利用上限と混同せず、「現在混み合っています」と再試行可能時刻を表示する。
- AIが使えない場合も、食事、身体、トレーニング、写真の手動保存を閉じない。
- バックグラウンド再試行は同じ要求を二重消費しないよう、リクエストIDで冪等化する。

## 6. 収益運用

目標実装:

- AdMobの固定バナー1枠
- ユーザーが選択する報酬広告によるAIクレジット付与
- StoreKit消耗型IAPによるAIクレジット購入
- 初回アカウント登録時だけ20クレジットを付与し、定期無料補充は行わない
- 健康・身体・食事・写真・位置・AI会話を広告ターゲティングへ使用しない
- 自動表示する全画面広告とApp Open広告は追加しない
- サブスクリプションは導入しない

週次に、AdMobの広告リクエスト、マッチ率、表示回数、eCPM、推定収益と、AIの推論回数、推論時間、混雑率を別々に確認する。個人単位で広告データとAI利用を結合しない。

月次に、Apple Developer Program、電気代、通信・ドメイン・バックアップ等の実費と広告・IAP収益を比較する。広告付与量、AI消費量、IAP価格は公開後の国別実績から調整する。

クレジット設定を見直す条件:

- AI運用費が広告収益を2か月連続で上回る
- AI利用上限到達ユーザーがアクティブユーザーの5%を超える
- p95待ち時間または混雑拒否率が継続的に悪化する
- 報酬広告または追加AI枠への明確な需要が確認できる

## 7. 実装順

1. 完了: 永続利用台帳と機能別上限
2. 完了: 構造化された`429`/`503`レスポンスと冪等化
3. 完了: iPhoneの残り回数・混雑表示
4. 完了: 匿名の運用サマリー
5. 要修正: TestFlight専用の利用枠無効化を撤去し、全配布版で制限を常時有効化
6. 正式公開前: オーナー専用登録キー、利用枠免除、失効、一般ユーザーとの分離を確認
7. 正式公開前: 通常テスターで上限到達、日付変更、利用計測、サーバー再起動、同時実行を確認
8. 正式公開後: 広告収益とAI負荷を月次評価

## 8. 完了条件

- サーバー再起動後も利用回数が維持される
- 機能別上限と全体混雑制御が独立して動く
- 上限到達時も手動機能がすべて利用できる
- TestFlightと正式公開の通常ユーザーには同じ残り回数とリセット時刻が表示される
- 利用台帳と運用集計に健康情報、本文、画像、直接識別子が含まれない
- 上限値をアプリ再配布なしで変更できる
- オーナーだけ機能別利用枠が免除され、一般ユーザーの制限と全体保護制御へ影響しない
- オーナー登録キーを失効した後は、新しいアクセストークンを発行できない
