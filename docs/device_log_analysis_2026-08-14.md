# BodyMode 実機ログ解析 2026-08-14

対象: iPhone 14 / TestFlight Build 14
解析元: 接続端末から取得した診断ログ、保存データ、retiredクラッシュログ
注意: 認証情報、写真本体、会話本文、端末識別子は本書へ記載しない。

## 結論

- Build 14で新しく発生したクラッシュは確認できなかった。
- 端末に残っていたクラッシュ3件はすべてBuild 13の同一watchdog停止であり、通知計測キューと`UserDefaults`監視のロック待ちが原因だった。Build 14へ入れた修正後の再発は引き続き監視する。
- AI無応答は単一原因ではない。失効済みQuick Tunnel、食事解析のHTTP 500、体型写真送信中の接続切断、サーバーが失敗文をHTTP 200で返す挙動、日次提案JSONの形式不正が混在していた。
- 最新の体型写真セットには正面・横・背面・腹部の4画像がすべて保存されていた。ただし、編集時の部分保存で未変更画像を上書き削除できるコード経路が存在したため、データ保持修正は必要だった。

## クラッシュ

| 件数 | 対象ビルド | 署名 | 判定 |
|---:|---:|---|---|
| 3 | 13 | `com.bodymode.notification-measurement` / `UserDefaultObserver.userDefaultsDidChange` / `__psynch_mutexwait` | 同一の既知watchdog停止。Build 14の修正後は新規記録なし |

App Store Connect上のクラッシュ提出が0件でも、端末内のretiredログには過去のクラッシュが残る。今後はビルド番号と発生日時を必ず照合し、古いログを新しい再発として数えない。

## AI通信

診断ログ222件のうち、`ai.transport`は40件、`ai.background`は34件、`ai.http`は7件だった。

| 症状 | 実機ログの根拠 | 対応 |
|---|---|---|
| 古い公開URLへ接続できない | 2026-08-12に失効済みQuick Tunnelで`cannotFindHost` | Tailscale公開URLを使用し、設定可能なURLは固定しない |
| 体型写真分析が切断される | Tailscaleの`/v1/body-photos/analyze-set`で`networkConnectionLost`を3回確認 | 4枚を1枚のコンタクトシートへまとめ、比較時も最大2画像に制限 |
| 食事写真解析が失敗する | 2026-08-13に`/v1/meals/analyze-image`のHTTP 500を7回確認 | 推論失敗を503として返し、リクエストID付きで原因を追跡 |
| チャットが返ったように見えて失敗文になる | 保存会話31件中7件がサーバーの定型失敗文。バックグラウンド側は完了扱い | 推論失敗や不正JSONを成功レスポンスへ置き換えず503にする |
| 日次提案を適用できない | `daily_recommendation.ai`のJSON読取失敗を6回確認 | サーバーで日次提案を正規化し、不正時は`keep_existing`でローカル提案を維持 |
| トークン発行が集中する | サーバー履歴にrate limitを確認。同じ回線の利用者がIP単位制限を共有していた | 利用端末単位の制限、全体上限、iPhone側の同時発行リクエスト統合へ変更 |

すべてのAIリクエストに`X-Request-ID`を付け、同じIDを端末診断へ保存する。次回から端末の失敗とサーバーログを1件単位で照合できる。

## 体型写真データ

- 保存エントリは15件。
- 最新セットは4方向すべてに画像データが存在した。
- 過去データには同日同方向の重複や画像なしエントリがあり、旧保存経路の影響が残っていた。
- 修正後は同日の未変更方向を保持し、利用者が明示的に削除した方向だけを削除する。

受入では、4方向保存、1方向追加、1方向削除、再編集、アプリ再起動を順番に行い、未変更写真が残ることを確認する。

## Watchログ

Watch連携には、計画選択、ワークアウト開始、HealthKit開始、セット開始・完了、休憩開始・停止、ワークアウト取消の記録が残っていた。今回の取得範囲ではWatch由来のクラッシュは確認できなかった。
