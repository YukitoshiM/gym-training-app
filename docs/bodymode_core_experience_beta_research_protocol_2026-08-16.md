# BodyMode コア体験 ベータ調査手順

更新日: 2026-08-16
対象: R1 今日の行動、R5 完了画面、R9 根拠表示
目的: 実装計画を確定するための実利用証拠を集める

## 1. 実施単位

期間は最低7日、目標は20人以上とする。人数が不足する場合も、最低5人から定性結果を記録する。少人数の割合を市場全体へ一般化しない。

割付:

- R1は全参加者を対象にし、同じ利用者日で表示と完了を対応させる。
- R5のA/B/Cは参加者IDの安定hashで固定割付し、期間中に同じ利用者の案を変えない。割付数は自然には均等にならないため、下記の事前発行コードを使う。
- R9はケース順を参加者ごとにローテーションし、先に見た説明から答えを学ぶ影響を減らす。
- 開発者本人、既存仕様を詳しく知る人、初見テスターを分けて集計する。

分析軸:

- 目的
- 経験レベル
- Apple Watch利用有無
- 提案カテゴリ
- readiness
- ローカル提案またはAI補正

### 調査実行キット

- `research-prototypes/bodymode_core_research_runner.html`: R5/R9の提示、5秒遮蔽、回答、固定割付、順序回転、JSON書き出し。
- `scripts/summarize_core_experience_research.py`: 複数の回答JSONを重複排除し、R5/R9を集計する。自由回答本文は集計へ転載しない。
- `scripts/audit_workout_export.py`: R8のCSV/JSON/XMLを構造監査する。記録セルの実値は監査JSONへ転載しない。
- `scripts/testflight_research_status.sh`: 外部グループまたは`--all-groups`で全グループの人数、状態、公開上限、割当ビルドだけをApp Store Connect APIから取得する。氏名・メールは要求・出力しない。
- `scripts/serve_core_experience_research.sh`: 調査HTMLだけを隔離した一時ディレクトリから配信し、無料Quick TunnelのURLを発行する。停止時にURLは失効する。

調査結果と受領したエクスポートはGit管理外の`.build/research-results/`と`.build/research-inputs/`へ置く。

## 2. R1 今日の行動

### 現行実装との差

研究用の利用分析は、イベント名、従来の`dimension`、許可された列挙プロパティを送れる。以下の計測点はローカル実装と単体テストまで完了しており、改訂した同意文を含むベータビルドの配布後に実測を開始する。

- 行動の表示イベント。
- 意図的に閉じた・拒否したイベント。
- 差替え先と差替え理由。
- 目的、経験、readiness、表示位置を同時に分析できる非機微プロパティ。
- 設定内の同意項目をテスターが発見した率。

前4項目は実装済み。最後の「同意項目の発見率」は、テスターへの1分質問で確認する。

2026-08-16 14:09 JSTの母数確認:

- `Reddit Beta`は外部グループで、公開リンクとフィードバックが有効。
- 公開リンク上限は50人。
- 割当は有効なBuild 22が1件。
- グループ参加者は0人。
- Build 22には本節の改訂計測が未配布。
- `Friends & Family`にはBuild 22をインストール済みの3人がいる。R5/R9のパイロットには利用できるが、R5の各案5人を満たすには不足する。

したがって、現時点の分析DB 0件から提案の良否や同意率を推測しない。

健康値や自由記述を送らず、列挙値だけを許可する。既存の単一`dimension`へ区切り文字で詰め込む方式は、40文字制限、版管理、誤集計のため採用しない。

### 必須イベント

| イベント | 必須dimension | 用途 |
| --- | --- | --- |
| `daily_recommendation_generated` | source, goal, experience, readiness | 分母 |
| `daily_action_impression` | actionCategory, position, goal, experience | 表示数 |
| `home_primary_action_started` | actionCategory, position | 開始率 |
| `daily_action_completed` | actionCategory, completionMethod | 完了率 |
| `daily_action_replaced` | fromCategory, toCategory, reason | 不適合理由 |
| `daily_action_dismissed` | actionCategory, reason | 無視と意図的拒否の分離 |

健康値、体重、食事内容、写真、自由記述本文は利用分析イベントへ含めない。

許可プロパティは列挙値に限定する。

| property | 値の例 |
| --- | --- |
| goal | diet, muscleGain, health, bodyShape, performance |
| experience | beginner, intermediate, advanced |
| readiness | good, normal, tired, rest |
| actionCategory | workout, steps, protein, mealGuidance, bodyWeight, waist, bodyPhoto, sleep, recovery, lightActivity |
| position | 0, 1, 2 |
| source | localRule, ai, mixed, user |
| reason | time, equipment, fatigue, pain, schedule, already_done, mismatch, other |
| completionMethod | manual, automatic |

`other`の自由記述は利用分析へ送らず、端末内または明示的フィードバックだけで扱う。

### 集計指標

- 行動開始率 = 開始ユーザー日 / 表示ユーザー日
- 行動完了率 = 完了ユーザー日 / 表示ユーザー日
- 開始後完了率 = 完了 / 開始
- 差替え率 = 差替え / 表示
- 1件以上完了した日 / アクティブ日
- 目的・経験別のカテゴリ順位

### 1分質問

1. 今日何をすればよいか、すぐ分かりましたか。5段階
2. 3件は多い、ちょうどよい、少ない、のどれですか。
3. 不要だった提案はどれですか。
4. 足りなかった提案はどれですか。
5. 実行しなかった主な理由は、時間、器具、疲労、内容不一致、既に実施、その他、のどれですか。

### 判断規則

- 目的別に開始率・完了率が高いカテゴリを主候補にする。
- 差替え率が高いカテゴリは、提案条件を見直す。
- 3件が多い回答が40%以上なら、主行動1件を初期表示し補助を折りたたむ案を試す。
- 3件が少ない回答だけで件数を増やさず、詳細モードへの候補一覧で対応できるか確認する。
- 目的別の表示ユーザー日が10未満なら、カテゴリ順位を確定せず定性仮説として残す。
- 95%信頼区間を併記し、少人数の数ポイント差で勝者を決めない。
- `daily_action_impression`が欠けた日は率の分母に使わない。

## 3. R5 完了画面

### 固定割付コード

参加者の氏名やメールをコードに含めない。各コードは1人だけへ渡す。

| 案 | 参加者コード |
| --- | --- |
| A | BM-001, BM-004, BM-007, BM-008, BM-010 |
| B | BM-002, BM-005, BM-009, BM-012, BM-014 |
| C | BM-003, BM-006, BM-011, BM-016, BM-023 |

既存のFriends & Family 3人には、まずA/B/Cから1コードずつ割り当てて進行不備を確認する。本比較は各案5人、合計15人が最低条件である。

### 比較案

| 案 | 最上部 | 主CTA |
| --- | --- | --- |
| A | 次回の仮提案 | 提案を見る |
| B | 達成、PR、完了セット | 完了して閉じる |
| C | ボリューム、重量、回数 | 詳細を見る |

### 測定

- 5秒後に「今日できたこと」を説明できるか。
- 5秒後に「次に何をするか」を説明できるか。
- 主CTA実行率。
- 詳細画面閲覧率。
- 計画変更提案の承認率・取消率。

### 暫定採用条件

- 理解度を最優先する。
- 差が小さい場合はBを採用し、次回仮提案を2番目に置く。
- 完了画面から計画を自動更新しない。
- 各案5人未満または完了画面10表示未満なら勝敗を確定せず、定性テストを追加する。
- 理解度が同等なら、操作数が少なく誤った計画更新が少ない案を選ぶ。

### R5採点基準

画面提示前に進行役が次で採点する。言い換えは意味が一致すれば正答とする。

| 問い | 正答 |
| --- | --- |
| 今日できたこと | トレーニング完了、8セット完了、PR更新、または今回の総量のいずれかを認識している |
| 次にすること A | 次回提案を見る |
| 次にすること B | 完了して閉じる |
| 次にすること C | 今回の詳細を見る |

自由回答が曖昧な場合は追加質問で正答へ誘導せず、`unscored`として別の進行役が後で判定する。

## 4. R9 根拠表示

### 3層プロトタイプ

1. 一文: 行動と最も重要な理由。
2. 判断材料: 使用データ、期間、欠損、信頼度。
3. 文献: 一般的傾向を支える研究とリンク。

提示用プロトタイプ:

- `research-prototypes/r9_rationale_5_second_test.html`
- 実際の回答取得には`research-prototypes/bodymode_core_research_runner.html`を使う。
- ケースA: 通常表示
- ケースB: 理由と判断材料
- ケースC: データ不足
- ケースD: 一般的研究根拠と個人判断の区別

### 5秒テスト

各画面で次の正答率を測る。

- 今日の行動を言える: 90%以上
- 理由を1つ言える: 80%以上
- 不足データの有無を判断できる: 80%以上
- 変更方法を言える: 80%以上

文献を開く率は成功条件にしない。必要な人だけが到達でき、存在しない引用や個人効果の断定がないことを必須とする。

記録方法:

- 画面を5秒表示した後に隠し、自由回答を先に取る。
- 選択肢は自由回答後にだけ提示する。
- 正誤は事前に定めた語句または意味一致で判定し、誘導質問で補正しない。
- タスク失敗時は、誤答、無回答、時間超過を分けて記録する。

### R9採点基準

| ケース・問い | 正答 |
| --- | --- |
| A 今日の行動 | 背中・肩のトレーニング、45分、または同義 |
| A 変更方法 | `変更`から別行動を選べること |
| B 提案理由 | 背中が4日空いている、睡眠・疲労が通常、のいずれか |
| B AI補正 | AI補正なし |
| C 不足データ | 睡眠、疲労、痛み、最近の活動量のいずれか |
| C 代替経路 | 不足情報を入力せず、そのまま開始できる |
| D 研究の意味 | 一般的傾向であり、個人効果の保証ではない |
| D 個人判断 | 最終実施日、睡眠、疲労、利用器具のいずれか |

## 5. R8 実ファイル収集票

各形式につき、個人情報を除いた2ファイル以上を取得する。

| 確認項目 | 記録内容 |
| --- | --- |
| アプリ名・版 | 出力元のバージョン |
| 端末設定 | 言語、地域、kg/lb |
| 文字コード・区切り | UTF-8、CSV delimiter等 |
| 日時 | 形式、タイムゾーン、夏時間 |
| セット | 通常、ウォームアップ、失敗、ドロップ等 |
| 負荷 | 外部重量、自重、追加重量、アシスト重量 |
| 種目 | 既定、カスタム、言語違い |
| 非筋トレ | 距離、秒数、メモ |
| 欠落 | 元アプリにあるが出力されない項目 |

Strong形式は公開資料上、重量単位列を持たない。このため、ユーザーによる単位確認なしに自動確定しない。

受領後の監査:

```bash
mkdir -p .build/research-inputs .build/research-results
python3 scripts/audit_workout_export.py \
  .build/research-inputs \
  --output .build/research-results/r8_export_audit.json
```

監査結果だけでは公式出力であることを証明できない。提供者から、アプリ名・版、地域、kg/lb設定、出力日時を別票で受け取り、ファイルfingerprintと対応付ける。

## 6. R5/R9結果の集計

参加者が書き出したJSONを`.build/research-results/raw/`へ集め、次を実行する。

```bash
python3 scripts/summarize_core_experience_research.py \
  .build/research-results/raw/*.json \
  --json-output .build/research-results/core_summary.json \
  --markdown-output .build/research-results/core_summary.md
```

同じ参加者コードと開始時刻の回答は重複として1件にまとめる。自由回答は自動判定せず、画面を見せる前に定めた正答基準で進行役が採点する。
