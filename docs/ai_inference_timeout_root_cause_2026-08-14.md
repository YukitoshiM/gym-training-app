# AI推論タイムアウト 原因分析（2026-08-14）

## 症状

- TestFlight Build 15でAIトレーナーの回答が240秒以内に返らない。
- 体型写真セット分析が「AIサーバーに接続できません」で失敗する。
- `/v1/health` は正常を返すため、表面上はサーバーが利用可能に見える。

## 確認した事実

- 公開URL、認証、Ollamaのモデル一覧取得は正常だった。
- Ollamaは `gemma4:12b` をコンテキスト長4096、並列数1で実行していた。
- APIは同時推論数2で、Ollamaの処理能力を上回る要求を投入していた。
- 失敗時刻のOllamaログには、約4,100から4,300トークンの入力を4095へ切り詰めた記録が連続していた。
- 切り詰め後は回答用の余白がほぼなく、1トークンだけを生成して無効なJSONになっていた。
- 最小プロンプトでも生成自体は1秒未満だったが、既存キューの待機で約31秒かかった。
- iPhoneまたはTailscaleが接続を閉じた後も、Ollama側の待ち行列は処理を続けていた。

## 根本原因

1. プロンプト長に上限がなく、4096トークンのモデル枠を使い切っていた。
2. APIの同時推論数2とOllamaの並列数1が一致していなかった。
3. API入口に短い待機上限がなく、失効した要求がOllama内部へ蓄積した。
4. ヘルスチェックがモデル一覧だけを確認し、直近の推論成否を見ていなかった。

## 恒久対策

- APIとOllamaの同時推論数を1へ統一する。
- 推論待機を8秒で打ち切り、混雑時はHTTP 503を返す。
- テキストと画像で別々のプロンプト文字数上限を設け、先頭の指示と末尾の最新入力を保持して中間を圧縮する。
- `num_ctx` と `num_predict` を明示し、回答用トークンを確保する。
- 推論開始、成功、失敗、混雑を構造化ログへ記録する。入力本文、画像、認証情報は記録しない。
- `/v1/health` に直近の推論状態を含め、失敗後は `degraded` を返す。

### アプリ送信前の制限

- ユーザーがAIチャットへ入力する文章は300文字までとする。
- AIサーバーの契約上限4,000文字は、日次提案などアプリ内部で生成する要求用に維持する。
- 会話履歴は保存済みデータを変更せず、送信時だけ直近8件、各600文字以内へ圧縮する。
- 通常の構造化コンテキストは約8,000文字、413再試行時は約4,000文字を目標に圧縮する。
- 送信用の会話履歴から端末内ID、日時、引用詳細を除き、roleとcontentだけを送る。
- AIへ渡すメモは500文字、食事リストの各項目は120文字までにする。端末内の原本は変更しない。
- 通常画像は長辺1,600px、JPEG品質0.8。体型写真は最大4方向を1,200pxのコンタクトシートへまとめる。
- 画像が1.5MBを超える場合だけ、品質と長辺を段階的に下げる。通常画像を不要に再圧縮しない。

## 再発確認

- 長い入力でもOllamaログに `truncating input prompt` が出ないこと。
- AIチャットが有効なJSONを返すこと。
- 体型写真セット分析が有効なJSONを返すこと。
- 同時要求時に2件目が短時間で503となり、Ollama内部へ待ち行列を作らないこと。
- 成功後の `/v1/health` が `status: ok`、`inference_ready: true` を返すこと。

## 反映後の検証結果

- サーバー単体テスト: 20件成功、失敗0件。
- 公開URL経由のAIチャット: HTTP 200、16.2秒、有効な構造化応答。
- 公開URL経由の体型写真セット解析: HTTP 200、28.5秒、有効な構造化応答。
- 上記2件で新しい `truncating input prompt` 警告は0件。
- 検証後のヘルスチェック: `status: ok`、`inference_ready: true`、待機0件。

更新直後の最初のチャットは128.9秒かかったが、更新前にOllama内部へ投入済みだった要求の終了待ちが含まれていた。古い要求の排出後に再測定した16.2秒を平常時の結果とする。
