## 2. 状態の流れ

`受信` → `トリアージ済み` → `対応中` → `実装済み・未配布` → `配布済み・確認待ち` → `解決済み`

例外状態は次の通り。

| 状態 | 用途 |
|---|---|
| 再発・調査中 | 一度直した課題が新しいビルドで再報告された |
| 設計待ち | 精度、安全性、外部データ利用などの判断が必要 |
| 重複 | 同じ正規課題へ統合済み。受信記録は残す |
| 方針決定 | 要望どおりには作らず、理由と代替方針を合意した |
| 対応しない | 対応しない理由を記録し、利用者が再開しない限り閉じる |

### 解決済みにする条件

- 自動判定できるUI・計算: 対象テスト成功、配布ビルドへの組み込み、実機またはTestFlightで1回確認
- 端末固有の不具合: 修正ビルドで報告者が確認するか、診断ログで同じ操作の成功を確認
- クラッシュ・データ損失: 再現テスト成功に加え、次の配布後7日間または十分な利用回数で再発なし
- AI通信: チャット、体型写真、食事の3経路をTestFlightで各3回成功し、7日間同種報告なし
- 主観的なUX: 実装しただけでは閉じず、少なくとも1人のテスターが改善を確認

## 6. 更新手順

1. `scripts/fetch_testflight_feedback.sh`でApp Store Connectから取得する
2. App Store Connect IDが本書にあるか照合し、新規だけ`TFB-xxx`を採番する
3. 症状ではなく原因・ユーザー価値が同じ正規課題へ統合する
4. 優先度、状態、完了条件、対象ビルドを更新する
5. 配布後は`実装済み`で止めず、上記の解決条件を満たしてからアーカイブへ移す
6. 再発時は正規課題を再オープンし、古い解決根拠を消さずに再発ビルドを追記する

個人情報、署名付きスクリーンショットURL、API認証情報は文書へ転記しない。
