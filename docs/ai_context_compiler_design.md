# AI Context Compiler設計

## 解決する問題

記録を増やすほどAIへ送る文章が増え、応答が遅く不安定になる問題を解決する。

ベクトル検索だけでは、関連記録を探せても次の問題は残る。

- 選んだ記録を最終的に文章としてLLMへ渡す必要がある。
- 全体傾向や記録間の関係が検索結果から抜ける場合がある。
- 入力サイズの上限を保証できない。
- 毎回の検索結果が変わると、コーチの判断も不安定になる。

BodyModeでは、全記録をLLMへ渡さない。端末内で記録を集計し、固定サイズの `CoachState` を生成して渡す。

## 基本構造

```text
端末内の生記録
    ↓
決定的な集計・差分計算
    ↓
CoachState（固定スキーマ・固定予算）
    ↓
必要時だけ過去エピソードを補足
    ↓
AIトレーナー
```

数値計算、期間比較、欠測判定はアプリが行う。LLMには、計算済みの状態とユーザーの質問を渡し、解釈と提案だけを担当させる。

## CoachState

```text
CoachState
- generatedAt
- profile
- goals
- currentStatus
- trainingState
- nutritionState
- recoveryState
- bodyTrend
- adherence
- constraints
- confirmedMemories
- missingData
- previousSuggestion
- suggestionResult
- dataQuality
```

### profile

- 年代
- 身長
- 経験レベル
- 目的
- 目標像
- 利用できる器具

### currentStatus

- 今日の体重・腹囲
- 今日の睡眠・疲労・歩数
- 今日の食事進捗
- 今日のトレーニング状態

### trainingState

- 直近7日と28日の実施回数
- 部位別セット数・総量
- 種目別の前回値と4週間傾向
- PR、RPE、計画達成率
- 最終実施日と空き日数

### nutritionState

- 7日平均カロリー・PFC
- 目標との差
- 記録日数と欠測日数
- 食事回数の傾向

### recoveryState

- 7日平均睡眠
- HRV・安静時心拍の本人基準との差
- 主観疲労
- 直近の高負荷日

### bodyTrend

- 7日平均と28日平均
- 前週差
- 体重・腹囲の変化速度
- 体型写真AIの最新コメントと撮影日

写真そのものはチャットへ送らない。写真解析APIの構造化結果だけをCoachStateへ入れる。

## 入力予算

AIへ送る入力を、内容ごとの固定予算で管理する。

| 内容 | 目安 |
|---|---:|
| ユーザー入力 | 最大300文字 |
| プロフィール・目標・制約 | 400文字 |
| 今日の状態 | 500文字 |
| 7日・28日集計 | 900文字 |
| トレーニング状態 | 700文字 |
| 食事・回復・身体傾向 | 700文字 |
| 記憶・前回提案・不足情報 | 500文字 |
| 過去エピソード | 最大3件・合計600文字 |

アプリ由来コンテキストは合計4,000文字以内とする。項目ごとの上限を超えた場合は、古い記録を切るのではなく、集計粒度を上げる。

## 階層集計

### 短期

今日と直近7日。詳細な数値を保持する。

### 中期

直近28日。週平均、増減、達成率へ集計する。

### 長期

全期間。最高値、本人基準、成功パターン、継続的な制約だけを保持する。

長期間の生ログや日別一覧は送らない。記録追加時に影響する期間だけを再集計し、キャッシュする。

## 安定性

- 同じ記録と質問からは同じCoachStateを作る。
- 数値の計算をLLMへ任せない。
- 入力にない事実を補わない。
- 欠測と共有オフを区別する。
- 朝に確定した提案は、小さなデータ変化では変更しない。
- 重要な目標変更はユーザー確認後に状態へ反映する。

## ベクトル検索の限定用途

ベクトル検索はContext Compilerの本体にしない。次のような質問で過去エピソードを思い出す補助としてだけ使う。

- 前にも同じ痛みがあった時は何をしたか
- ベンチプレスが伸びた時期に何をしていたか
- 過去に続けやすかった食事方法は何か

検索結果は最大3件・合計600文字とし、CoachStateの固定項目を置き換えない。検索失敗時も通常のAIチャットは動作する。

## サーバープロンプトの予算

アプリ側だけを圧縮しても、サーバーの指示文と論文RAGが長ければ解決しない。サーバー側も次の予算を持つ。

- コーチ・安全・出力形式の指示: 1,200文字以内
- アプリのCoachState: 4,000文字以内
- 論文根拠: 上位3件、合計1,200文字以内
- ユーザー入力: 300文字以内
- 最近の会話: 直近4往復、合計1,200文字以内

最終的にはトークナイザーで入力トークン数を計測し、回答領域を確保したうえで送信する。単純な先頭・末尾の文字切りは最終安全装置としてだけ使う。

## 実装順序

1. `CoachState` と各集計モデルを追加する。
2. 既存の `CoachContextBuilder` を `CoachStateCompiler` へ段階的に置き換える。
3. 7日・28日・長期集計の単体テストを追加する。
4. コンテキストの項目別予算と全体4,000文字制限を追加する。
5. サーバーの長い固定プロンプトを1,200文字以内へ整理する。
6. 論文RAGを上位3件・合計1,200文字へ制限する。
7. 同一入力で提案が安定するか評価する。
8. 必要性を確認してから、過去エピソード用のベクトル検索を追加する。

## 成功条件

- 記録件数が増えてもAI入力サイズが増え続けない。
- 主要な数値と傾向が入力から欠落しない。
- 同じ状態に対する提案が安定する。
- AI未接続でも集計済み状態をホームへ表示できる。
- チャットの平常時応答が60秒以内に収まる。
- 入力超過とOllamaのプロンプト切り詰め警告が発生しない。
